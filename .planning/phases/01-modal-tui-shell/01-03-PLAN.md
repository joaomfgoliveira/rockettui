## Phase Goal

Roadmap goal (verbatim): A runnable ratatui app with the sidebar + messages + input layout, fake rooms, and Normal/Insert/Command modes. (No user story is framed in ROADMAP; see plan 01-01.)

<objective>
Turn the single-key lookup of the skeleton into the real Vim key matcher: counts (`5j`), multi-key sequences through a trie (`<C-w>h`, `gg`), a ~1 s timeout driven by the event loop, pending keys shown in the status line, plus pane focus with Ctrl-w, the complete Normal-mode keymap and the per-pane motion router.

Purpose: every later navigation feature (sidebar sections, message scrolling, input-pane motions, Insert mode) rides on this matcher, the Normal keymap and the router defined here; plans 01-04 and 01-05 run in parallel afterwards precisely because this plan owns the keymap, the Action variants and the motion routing.
Output: src/input/trie.rs, src/input/matcher.rs, format_keys, trie-backed keymap with all Normal rows, KeyTimeout deadline, focus model, open_room, motion router, status bar with room and pending keys.

Scope note (file count): 11 files, one above the soft threshold of 10 and well below the 15-file blocker. Ten are the new matcher engine (trie.rs, matcher.rs, key.rs, input/mod.rs) or one wiring point it must reach (keymap, Action, App, reducer, run loop, status bar). The 11th, src/ui/mod.rs, only gains task 3's two render tests (`focused_pane_has_thick_border`, `status_shows_mode_room_and_pending`) in its existing `ui::tests` module and no production code; it was edited but unlisted before plan-check iteration 2 of the re-plan. The tests stay there rather than moving to src/ui/status.rs because the border test renders the whole view, not the status row, and the thick border needs no renderer change (plan 01-02 already passes each pane's focus flag to `pane_block`). The sidebar's handling of Enter (open the room, D-02) moved to plan 01-04, which rewrites src/app/sidebar.rs anyway, so this plan no longer touches that file.
</objective>
